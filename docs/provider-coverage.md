# Provider coverage and roadmap

Status: incremental inventory, not an assertion of complete provider support. Reviewed the repository and linked provider documentation on 2026-11-04; provider APIs, models and SDK versions change. No paid calls or external mutations were made. The goal is to account for **all** options on each explicitly supported API, including nested fields, transport and lifecycle semantics; the table is a starting point rather than a complete field inventory.

## What exists

The workspace has `agent_weave_openai` backed by `openai_dart` 11.0.1, plus the `ChatModel` extension interface (`docs/providers.md`). The new `agent_weave_anthropic` uses the native Messages API through `anthropic_sdk_dart 9.0.1`, with offline fixtures. The `agent_weave_openrouter` package wraps Chat Completions with selected typed OpenRouter options and offline fixtures. The `agent_weave_together` package provides native Chat Completions and offline fixtures. There are no dedicated Vercel Gateway or Cloudflare packages. `OpenAIChatModel` maps runtime history and function tools to streamed Chat Completions and supports a typed SDK `configure` callback. OpenAI-compatible base URLs can be supplied through the SDK client, but neither this configuration nor custom provider support establishes endpoint-specific compatibility. Runtime currently interprets only part of the returned stream, as documented in [the OpenAI audit](openai-options-audit.md). `OpenAIPlatformApi` is a restricted JSON/raw transport, not a complete native or streaming provider adapter.

## Architecture requirements

1. Key capabilities by **provider, API protocol, endpoint and model**, distinguishing supported, unsupported and unknown. Do not advertise unconditional tools, media or structured output for every model. Preserve the core runtime's authoritative conversation and registered tools while allowing explicit provider options; reject incompatible combinations rather than silently ignoring them.
2. Reuse an actively maintained typed Dart SDK when it actually represents the endpoint and preserves required fields. `openai_dart` is already useful for OpenAI and the subset of compatible wire formats its request types model; it is not an Anthropic SDK or proof of arbitrary extension support. Evaluate candidate native SDK maintenance, license, streaming, cancellation, types, unknown fields and release cadence before adoption. Where a specific field or union is missing, reproduce the omission against official docs and submit a focused upstream issue or patch with serialization and round-trip tests; do not fork preemptively.
3. Define explicit provider-specific typed options plus a controlled forward-compatible extension mechanism where transport supports it. Separate request fields, query parameters, request-scoped headers, multipart/binary data and SSE/WebSocket transport; preserve auth, cancellation, timeouts and safe retry/idempotency semantics. Never log credentials or sensitive replay blocks. An escape hatch alone does not implement orchestration.
4. Preserve raw provider continuation privately and round-trip every relevant block in order. Map function calls, client-executed computer/custom tools, hosted tools, approvals, tool results and IDs distinctly; do not force all results into a function-output schema. Preserve refusal, errors, finish reasons, structured output, citations, reasoning, media, cache and usage/provider metadata without presenting private continuation as UI text.
5. Inventory all create/retrieve/list/delete/cancel/query operations, paging, background jobs, cache and storage settings, file/media upload, realtime and model-specific limits separately. Make explicit whether each is typed SDK access, raw escape hatch, integrated runtime behavior, fixture-verified or live-verified.

## Verification and upkeep

- Maintain a versioned machine-readable inventory per provider/API/endpoint: official source URL and revision/date, request and response field/union, defaults, constraints, SDK representation, adapter handling, tests and status. Generate a human-readable coverage report and fail CI on unexplained inventory/spec changes when a reliable machine-readable spec is available; manually review provider changes where it is not.
- Offline contract fixtures must assert exact request JSON/headers/query and parse provider event sequences. Cover text, schema, fragmented parallel tool arguments, multi-turn replay, hosted vs client tools, rejection, malformed/unknown events, errors, EOF, usage, caching markers, pagination, cancellation, privacy and retry. Add endpoint-specific incompatible-option tests. Include a mock HTTP consumer scenario for each claimed compatible provider, not just SDK unit tests.
- Separately run explicitly authorized, spend-limited live smoke tests per provider/model/endpoint for text, tools, structured output, usage and any claimed media/cache behavior. Record model, date, capability, output and whether a real cache hit occurred; a fixture, reexport or HTTP 200 is not proof of real orchestration. Re-run after SDK or provider-spec changes. Do not treat this roadmap as completed until every supported surface has an inventoried, tested status and known exclusions.
